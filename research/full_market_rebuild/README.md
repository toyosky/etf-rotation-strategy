# 全市场 ETF 趋势重建实验（研究草案 V1）

状态：exploratory；独立于实盘 Top1，不得自动修改 production 信号。

## 研究问题
在动态、按历史时点可交易的 ETF 池中，逐只判断趋势是否重建（而不是全市场强制选 Top1），是否降低换仓、改善扣费后的组合表现？随着池宽增加，假信号数量是否上升？

## 已冻结的信号基线
复用 `automation/build_fundamental_audit_trigger.py` 的 `calc_ols`：
- 收盘后 26 日对数价格加权 OLS，半衰期 10 日；annual 从 <=0 上穿 0；
- 上穿后第 1–3 交易日，annual>0，单日 R² 改善，且 R² 高于上穿日，则首个满足者构成 REBUILDING_QUALIFIED；
- 每次 episode 只计首次合格；研究不得事后从多个合格日期挑最好一天。
- R² 不代表绝对趋势强度，不能直接以 R² 高低选 Top1。

## 样本和点时约束
- 使用历史实际上市、可交易 ETF 集合；不能使用 2026 年当前存续池回填旧年份；需核实退市/清盘 ETF 和类别历史快照。
- 当日收盘计算、次一交易日开盘成交；交易数据不能使用未来复权因子判断交易当天可成交的价格/溢价。
- 剔除杠杆/反向基金、不可交易日、流动性不达标者，规则预先冻结。
- 同指数不同基金去重和相关性约束只能管理风险，不能偷偷退化为按得分选 Top1。
- QDII/LOF 净值及溢价应当保留 first_seen_at 的 PIT 证明；没有历史 PIT 证据时，单列“不含溢价”的研究与可交易性上限，不能假定已回避高溢价。
- 验证方案：2021–2024 研究，2025–2026 验证；2026 只统计实际已有数据；至少进行池宽分组/独立阶段验证。

## 实验臂
A. 当前 OLS Top1（沿用成本、执行与候选条件）
B. 独立重建：首次合格后单次建仓
C. 独立重建：沿用 `research/rebuild_pyramiding_backtest.py` 的阶段加仓结构
D. 多重建组合：事件独立进出；预先固定资金槽位、同一底层最多一只、相关性约束，允许现金，不做每日冠军争夺

退出测试需明确 20 日固定观察窗和趋势失效退出是不同实验；回测脚本现有 20 日 episode 限制不能直接当成无限期真实持仓策略。

## 指标
- 每年事件数、合格率、同日并发峰值、可交易候选数
- 事件后 5/10/20/40 日收益、P10、MAE/MFE、确认前涨幅
- CAGR、MDD、Calmar、持仓利用率、换手、费用、滑点、空仓天数
- 池宽 20/50/100/全市场，对比新增事件质量和组合风险
- 按商品、行业、跨境、宽基分层；失败/存活 ETF 分层
- 全量交易日志、拒绝原因、每次建仓依据可追溯

## GitHub 优先的数据存储契约
- `research/full_market_rebuild/` 存规范、代码和小型指标 JSON/CSV。
- 批量历史 OHLCV 使用分年 / 分交易所的 ZSTD Parquet，附 manifest：as_of、源、复权口径、symbol/date 行数、SHA256、抓取时点、补丁记录。
- 常规大批量原始数据不提交普通 Git 历史。优先通过 GitHub Actions 产生**带版本的 GitHub Release 附件**作为固定研究数据集；每次研究锁定 Release tag + 附件 checksum。需要 Git 版本绑定且体积受控的冷快照才用 Git LFS。
- GitHub Actions artifact 只放短期日志，不作为永久存储；Actions cache 也不是原始数据仓库。
- 发布前评估 GitHub Release 单文件大小限制、仓库配额、下载/更新成本；尽量做到历史归档不变，增量按月更新，季度整理快照。
- 小型当前每日信号仍可放 Supabase；**不得因为全市场回测向 `public.daily_bars` 整库回填**，该表继续承担实盘小池数据。
- 不上传密钥、原始第三方付费受限行情或无法合法再分发的数据；必要时只提交下载脚本和校验清单。

## 启动前的数据缺口（2026-10-20 核对）
`instrument_metadata` 约 2064 行，其中 ETF distinct symbols 1644；`public.daily_bars` 当前仅 19 只、32767 行，最大日期 2026-10-19。metadata 的 `has_daily_bars` 标记不能等同当前表内覆盖，应审计其语义和状态。

现有 `research/FULL_MARKET_OLS_STORAGE.md` 描述的是此前 Supabase Storage 的完整行情归档流程；这次研究选择 GitHub 存储**新建立的冻结研究数据快照**，不能误称旧对象已经迁至 GitHub。

## 实施顺序与验收
1. 探查现有研究归档是否仍能读取，核实行情来源、点时元数据及退市覆盖；
2. 编写数据补齐与 Parquet manifest 校验流水线，首批发布 GitHub Research Data Release；
3. 在相同样本、相同费用假设下重跑 A/B/C/D；
4. 输出分时期、分资产、池宽稳健性报告并形成单独的模拟信号，不切换实盘。
